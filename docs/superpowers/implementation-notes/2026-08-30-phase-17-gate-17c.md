# Phase 17 Gate 17C implementation notes

## Scope and status

Gate 17C implements Survival material conservation for the two initially
supported DETAIL materials, stone and dirt. It does not implement Gate 17D UX,
normal Survival acquisition/crafting, FULL/64-unit conversion, tool tiers,
harvest tiers, progression, generated/player provenance, or a second edit
queue. Work remains uncommitted on `feat/small-voxel-tools`.

## Task 14 - canonical material-unit mapping and action policy

- RED: focused compile failed only because `DetailSupportDefinition`, the
  registry mapping APIs, and the action-policy types were absent.
- GREEN: stone maps to `gaia:stone_detail_unit`; dirt maps to
  `gaia:dirt_detail_unit`; loading rejects malformed, missing, duplicate, or
  non-64 standalone unit mappings.
- `Phase17DetailActionPolicy` is pure. Precision recovery requires the existing
  `DETAIL_PRECISION` capability. Survival precision yields one detail unit;
  Creative yields none. A compatible uniform 64/64 coarse result may yield one
  FULL block item; partial/mixed results yield none.

## Task 15 - composition and coarse hardness

- RED: focused compile failed because the composition aggregator and the
  resolved-hardness policy overload were absent.
- GREEN: canonical subvoxel index order derives occupied count, uniformity, and
  maximum material hardness. Occupancy fraction never scales hardness.
- Unknown materials fail closed. Survival coarse interaction additionally
  requires every occupied material to have an explicit detail-unit mapping.
- The result enters the existing `BlockInteractionPolicy`, `BreakRule`, and
  `BlockBreakTracker`; there is no DETAIL break tracker.

## Task 16 - precision removal with guaranteed INSERT

- RED: `SurvivalDetailEditTransaction` and its bounded result were absent.
- GREEN: one matching unit is completely reserved, active-slot first, before
  one `sculptParentSubVoxel` CAS. Inventory-full, invalid, unavailable, stale,
  and rejected outcomes produce zero world/inventory deltas.
- A pre-apply mutation exception rolls back the reservation before propagating.
  `DetailMutationEventDispatchException` preserves the exact canonical outcome;
  when that outcome is APPLIED, the reserved recovery is committed exactly once
  and the diagnostic is reported as `APPLIED_WITH_NOTIFICATION_FAILURE`.
- Inventory notification exceptions with `stateChangeApplied=true` follow the
  same applied-state rule and are never blindly retried.
- Result audit is exact: removal records `occupiedDelta=-1` and
  `inventoryDelta=+1`.

## Task 17 - precision placement with guaranteed EXTRACT

- RED: the planner had INSERT only, and the Survival transaction had no
  placement branch.
- GREEN: `reserveExtraction` uses the same deterministic preferred-slot-first
  order and immutable reservation batch. One matching unit is reserved before
  one CAS and committed only after APPLIED.
- Wrong/no unit, occupied destination, UNKNOWN/FAILED, overlap, and stale CAS
  reject without consumption. FULL AIR and cross-parent/cross-Chunk candidates
  remain the Gate 17A canonical candidates.
- Result audit is exact: placement records `occupiedDelta=+1` and
  `inventoryDelta=-1`.
- Applied-state mutation notification failure commits extraction exactly once;
  pre-apply failure still rolls back.

## Task 18 - coarse Survival break

- RED: the parent transaction was Creative-only and had no output reservation.
- GREEN: `DetailParentComposition.fromSupported` validates canonical occupied
  materials. Uniform compatible 64/64 DETAIL reserves and commits exactly one
  FULL-block WorldItem. Partial single-material and mixed DETAIL remove with
  zero output. No path emits micro-item explosions.
- WorldItem capacity is reserved before the one parent CAS. Mutation rejection
  rolls it back. Commit/rollback use the existing
  `WorldItemSpawnCommitResolver`; unresolved state is latched and reconciled on
  close.
- Applied-state parent-mutation notification failure still commits the one legal
  full-block output. An unresolved reservation blocks both Creative and Survival
  execution until close reconciliation, and fatal errors remain observable.
- Survival coarse timing uses the existing `BlockBreakTracker` and maximum
  hardness. Creative remains immediate.

## Task 19 - controller, provisioning, and persistence

- RED: the sole controller returned `detail_survival_deferred`; the explicit
  provisioner type was absent.
- GREEN: `BlockInteractionController` dispatches one Survival precision or
  coarse transaction from the existing route and target. It adds no raycast,
  edit queue, retry, mutation authority, inventory authority, or renderer.
- `GameSessionFactory` composes the existing services and registers coarse
  transaction reconciliation at shutdown.
- Development-only commands `detail-stone` and `detail-dirt` replace the right
  hand with one chisel and left hand with one selected 64-unit stack through
  `InventoryService.replaceSlot`. They are never invoked automatically by New
  World bootstrap.
- Existing inventory and WorldItem codecs already persist generic
  `ResourceLocation` plus integer count. The three standalone identities
  round-trip without production codec or save-format changes.

## Windows runtime attempt

The production GLFW path launched and reached the main menu with explicit
`detail-stone` provisioning configured. The Computer Use adapter moved the
cursor and updated menu hover state, but its instantaneous click/key injection
was not sampled by the game's fixed-step pressed-edge input, so it could not
enter New World. The process then handled Alt+F4 and exited cleanly; Gradle
reported `BUILD SUCCESSFUL`. Survival remove/place/coarse/save runtime cases
remain manually unverified rather than inferred from automation.
