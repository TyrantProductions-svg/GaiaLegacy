# Phase 16 Gate 16E Implementation Notes

## Scope

Gate 16E adds development-only acceptance tooling, deterministic measurements, two measured mesh-memory safety policies, exact-sized builder allocation, documentation, and closure preparation. Gates 16A through 16D remain frozen. No Phase 17 harvest/economy behavior or Phase 19 natural DETAIL generation is implemented.

## Resource policy history

The legal 1,024-parent checkerboard originally produced 47,185,920 detached bytes. With 32 completed-undrained results, count-only scheduling admitted an unsafe roughly 1.51 GiB output envelope. The first intervention added the 8,388,608-byte total hybrid output cap and typed `MESH_OUTPUT_LIMIT_EXCEEDED` failure without changing canonical data.

Post-cap `-Xmx512m` stress then measured 259,522,560 detached output bytes and approximately 508.8 MiB peak heap. The second intervention added one 134,217,728-byte all-Chunk CPU mesh budget in the existing `ChunkMeshManager`. FULL, DETAIL, and hybrid work reserve complete active-build memory; global pressure remains queued, while a single impossible job receives distinct `MESH_MEMORY_BUDGET_EXCEEDED`.

Attribution established that the remaining 95% to 97% heap peaks were dominated by dead `float[]` churn from geometric builder growth, `toArray()`, and the public `ChunkMeshData` defensive copy. The original stress resolver also reconstructed render metadata per lookup, unlike production's stable `BlockRegistry.resolve()` objects, and materially exaggerated allocation pressure. The corrected resolver produced identical geometry and hash.

Step A changed the builder to allocate one exact-sized backing array from the existing preflight and verify its write cursor. The existing `toArray()` and public defensive copy remain. Production-equivalent unperturbed `-Xmx512m` results then reached the controller target:

These figures are bounded M2 evidence, not universal hardware guarantees. Step B ownership transfer is **NOT NEEDED**. Step C trusted `ChunkMeshData` ownership is **NOT NEEDED**. Both remain closed without new profiling evidence.

The old artifact resolver evidence remains diagnostic only. Final acceptance uses cached stable `BlockRenderInfo`, material, and texture-region objects equivalent to production. Setup/restore is completed before the warmed mesh-lifecycle measurement window; unperturbed runs perform no explicit GC.

## Development tooling

`DetailDebugInputController` is composed only when the existing development shortcut flag is enabled. It reads exact `PlayerBlockTargeting`, calls `DetailDebugTools`, and constructs ordinary `GaiaInteractionContext` requests for `GaiaDetailMutationService`. It owns no repository, Chunk, storage, revision, dirty, mesh, or save authority.

Controls are F9 inspect, F10 convert, F11 fill, F12 clear, `9` cycle fixture,
and `0` apply fixture. `Ctrl+F9`/`Ctrl+F10` remain compatibility aliases. The
dedicated number-row controls were added tests-first after real Windows
acceptance showed that `Alt+F9` opens the Windows/NVIDIA recording overlay and
synthesized Ctrl chords release before the fixed-step input snapshot. Runtime
output is capped at 2,048 characters; mesh diagnostic text is capped at 512.
Heavy multi-parent stress remains tool/test-only.

Fresh-process acceptance is the decision point for any later dedicated optimization.

## Windows runtime acceptance

The production GLFW/OpenGL path ran on Windows with Microsoft OpenJDK
21.0.11+10-LTS. Development shortcuts created an asymmetric seven-subvoxel
fixture at canonical parent `[156,26,243]`, Chunk `[9,15]`, revision `4839`.
The canonical occupancy was `0x0480010040000029` and its deterministic hash was
`2f65a9bce5596a7bc053d701ccff01469fcb6be683fba1ad36ff099b04a0caa7`.
Rendering installed normally, the collision resolver reported seven boxes, and
the production raycast selected local `[2,2,3]`. Save & Quit returned to the
main menu and exited with code zero. A genuinely fresh JVM loaded the same
world and reproduced the exact parent, revision, occupancy, hash, local target,
material, collision-box count, and installed mesh phase.

Window resizing produced a fresh rendered frame. A later closure-precondition
run exercised Alt+Tab to another application and reactivated Gaia. The game
returned paused, resumed with mouse capture, and showed no replay of F9-F12,
`9`, or `0`, no repeated mutation, and no stuck movement. Native Apple Silicon
acceptance was unavailable and is `NOT RUN`.

Startup, load, and the post-save catalog refresh took minutes in this existing
save catalog. The closure-precondition attribution classified this as **S2 —
pre-existing Phase 14/catalog issue**, not a Phase 16 DETAIL regression. The
real six-directory root produced three `SaveRepository.summaries()` times of
98.135, 94.763, and 90.399 seconds. Isolated copies measured a small FULL-only
save at 2.046/1.503/1.495 seconds, a small current save with 11 indexed Chunks
and two DETAIL-bearing payloads (196 DETAIL-extension bytes total) at
9.679/8.636/8.328 seconds, and the pre-Phase-16 slow save at
2.350/1.551/1.509 seconds for summary rows plus about 80 seconds for a complete
289-index-entry payload inventory. That old save contains 578 physical Chunk
payload files, 19,422,431 bytes, and zero DETAIL extensions.

Source and live thread evidence agree on the dominant path:
`SaveRepository.summaries()` calls Phase 14 publication observation and
`StreamedSessionSaveTarget.restoreSession()`; `openBoundedReadView()` resolves
every indexed payload slot, and WorldItem physical-page validation can request
each decoded generic payload again. `StreamedChunkCodec` validates the bounded
voxel/extension framing and checksums, but catalog listing never invokes
`DetailBlocksCodec` or reconstructs `DetailStorage`. The earlier restore-allocation
JFR observation is therefore not the catalog explanation. The issue remains a
separately scoped product-performance risk; Gate 16E changes no save/catalog
production code.

The closure-precondition runtime could not truthfully complete the remaining
physical movement collision matrix, unload-radius leave/return cycle, or an
in-game `MESH_OUTPUT_LIMIT_EXCEEDED` presentation. Desktop automation can issue
discrete keys but could not hold movement through fixed simulation frames, and
the bounded runtime controls deliberately expose only one-parent fixtures.
Automated coverage remains valid but is not substituted for these manual cases.

## Closure review corrections

The first independent closure review found two release-blocking composition defects. Tests first reproduced all three mixed Chunk/WorldItem transaction forms: an ordinary exact capture restored older durable DETAIL, page replacement treated changed DETAIL as an opaque-extension conflict, and page removal retained older durable DETAIL. `StreamedWorldItemPageBackend` now keeps exact-capture `detail-blocks` authoritative while preserving independently owned durable extensions and applying only the page-owned replacement/removal. The three REDs are GREEN and the adjacent Save & Quit proof path remains GREEN.

The same review found that the two expected per-revision mesh resource diagnostics were also entering the fatal worker-failure queue. The repository-latched `MESH_OUTPUT_LIMIT_EXCEEDED` and `MESH_MEMORY_BUDGET_EXCEEDED` states now remain bounded mesh diagnostics and no longer terminate the game session through `pollFailure`; unexpected worker/upload failures retain their existing fatal path. Both resource-policy REDs are GREEN, the generic worker-failure regression remains GREEN, and the mesh lifecycle focused classes are 72/72 GREEN.
