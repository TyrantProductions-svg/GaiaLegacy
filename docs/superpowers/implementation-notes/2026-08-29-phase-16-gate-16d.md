# Phase 16 Gate 16D Implementation Notes

## Scope and frozen baseline

Gate 16D extends only the existing owning-Chunk CPU mesh generation path with canonical DETAIL geometry. Gates 16A, 16B, 16C1, and 16C2 remain frozen. This gate adds no debug/runtime tooling, survival tooling, material economy, shader change, vertex-format change, mesh queue, GPU lane, render object per DETAIL parent, collision/raycast/persistence change, or independent revision authority.

## Mesh authority and detached input

- `ChunkRepository` still issues the exact revisioned `ChunkMeshingClaim`.
- `ChunkMeshingClaim` remains the separate `claimId/key/revision/input` lifecycle capability.
- `ChunkMeshInput` remains exactly nine `ChunkSnapshot` components. It owns no claim, repository, World, game registry, or GPU capability.
- `QuarterVoxelSampler` owns only a `ChunkMeshInput`; it wraps quarter coordinates deterministically through the immutable eight-snapshot horizontal halo and treats vertical coordinates outside world height as FULL AIR.
- `ChunkMeshBuilder` owns only the existing `BlockRenderResolver`. Its worker path performs no mutable `World`, `ChunkRepository`, `Chunk`, OpenGL, or game-session access.
- Detached `ChunkMeshData` remains the single CPU result for the owning Chunk. Its SHA-256 `canonicalHash()` covers the exact ordered float payload using canonical float bits and does not depend on object identity.
- Existing owner-thread claim/revision validation, upload, replacement, destruction, and aggregate publication remain unchanged.

## FULL-only fast path

`ChunkMeshBuilder` first detects whether the center contains DETAIL or a relevant neighbor boundary/corner contains DETAIL. With no relevant DETAIL, it executes the legacy FULL traversal and vertex order unchanged. The internal package-private `ChunkMeshInput.fullOnlyBlock` compatibility seam delegates to the existing fail-closed byte boundary, so an incorrect fast-path precondition cannot reinterpret a DETAIL parent as AIR. Existing exact FULL vertex-layout, AO, face-culling, Chunk-edge, negative-coordinate, hash, and lifecycle regressions remain GREEN.

## Canonical quarter geometry

The quarter sampler returns a cached immutable `(runtime block ID, FULL|DETAIL provenance)` value. FULL non-AIR expands logically to all 64 quarter samples without allocating a DETAIL state; FULL AIR expands to empty FULL samples; DETAIL reads immutable canonical occupancy/material by X-fast index `x + 4*y + 16*z`.

The hybrid builder visits center parents in deterministic X/Y/Z order and DETAIL subindices in ascending canonical order. A renderable occupied DETAIL cell emits an oriented facelet only when the adjacent canonical quarter sample is not a renderable occupied surface. Thus:

- adjacent occupied DETAIL cells eliminate the internal face regardless of material;
- DETAIL/FULL occupied regions are hidden on both sides;
- DETAIL/DETAIL occupied-to-occupied regions are hidden and occupied-to-empty regions are single-sided;
- DETAIL/AIR and DETAIL/non-renderable boundaries remain visible under the existing rendering rule;
- cardinal Chunk boundaries use the immutable neighbor snapshots; diagonal snapshots remain available to AO;
- every coordinate is calculated directly from integer quarters and is exactly one of `0`, `0.25`, `0.5`, `0.75`, or `1` relative to the parent.

DETAIL facelets deliberately remain unmerged in Phase 16 v1 because each subvoxel owns a complete material face texture. This is the approved UV contract. Hidden-face elimination still reduces a uniform 64-cell DETAIL cube from 384 candidate faces to its 96-quarter-face outer shell.

## FULL/DETAIL seam, UV, and AO

When a FULL face neighbors DETAIL, or its AO neighborhood reaches DETAIL, the builder creates a deterministic 4x4 visibility mask. A quarter region is emitted only when the corresponding neighbor quarter sample is not a renderable occupied surface. The DETAIL side uses the identical canonical sampler, giving exactly one surface for visible complementary regions and zero surfaces for hidden regions.

Visible FULL quarter patches retain the original parent-face parameterization by cropping the existing atlas region at the patch's integer quarter coordinates. DETAIL facelets map their owning material's complete block-face region. Mixed materials therefore keep separate canonical atlas ownership and no new registry is introduced.

Quarter-grid AO reuses the existing two-side-plus-corner rule. Opaque and cutout renderable samples occlude; transparent or non-renderable samples do not. The three immutable samples may cross parent, Chunk, or diagonal-Chunk boundaries. FULL mask merging uses fixed row-major seeds, +U expansion, then +V expansion, and is permitted only when every included facelet has the same uniform four-corner AO signature. Nonuniform or incompatible AO remains split. No merging occurs across parent boundaries.

## Checked geometry bounds

The output remains the existing non-indexed ten-float vertex format, so index count is exactly zero.

For the accepted DETAIL cap alone:

```text
1,024 DETAIL parents * 64 occupied cells * 6 faces
    = 393,216 facelets
393,216 * 6 vertices
    = 2,359,296 vertices
2,359,296 * 10 floats
    = 23,592,960 floats
23,592,960 * 4 bytes
    = 94,371,840 vertex bytes
```

The checked hybrid per-input bound also accounts for clipped FULL faces. Its conservative maximum at world height 256 is:

```text
(65,536 - 1,024) FULL parents * 6 faces * 16 quarter patches
    + 1,024 DETAIL parents * 64 cells * 6 faces
    = 6,586,368 facelets
    = 39,518,208 vertices
    = 395,182,080 floats
    = 1,580,728,320 vertex bytes
```

All facelet, vertex, float, byte, growth, and final array-limit arithmetic uses `Math.multiplyExact`, `Math.addExact`, or `Math.toIntExact`. Output begins with at most 4,096 floats and grows only as required up to the checked per-input bound; the theoretical bound is not eagerly allocated. Exceeding the bound fails explicitly rather than dropping geometry.

The production adversarial fixture fills all 1,024 DETAIL parents with a 32-cell checkerboard. It emits 196,608 facelets, 1,179,648 vertices, 11,796,480 floats, zero indices, and 47,185,920 vertex bytes. It completes without overflow, spans exactly the 16x4x16 center bounds, produces a canonical 32-byte hash, and remains below the checked input limit.
