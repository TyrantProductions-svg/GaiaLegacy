## Objective

Unify GaiaLegacy's functional product screens and gameplay HUD as one readable
**world-first cosmic survival** presentation system. Gaia's environment carries
the emotional identity of title/product-shell screens; deep-space engineering
remains the restrained component language. The system must extend the existing
renderer, screen navigation, and HUD composition rather than introduce parallel
authorities.

The intended balance is environmental imagery first, deep navy for directional
legibility, Gaia cyan for interaction, sparse Legacy violet for identity, and
warm gold only for rare warning or special emphasis. Typography and state
clarity always outrank decoration.

### DPI, filtering, and coordinates

`RenderSurfaceMetrics` distinguishes logical window size, framebuffer size,
and independent X/Y content scales. `UiLayoutContext` derives logical UI
extents from framebuffer/content scale and independently rounds each edge into
framebuffer pixels. Window pointer coordinates map back into the same logical
space. Existing tests cover 100%, fractional Windows scaling, asymmetric
scales, resize, and Retina-like fixtures.

The current `OpenGlUiGpuBackend.createTexture` hard-codes nearest sampling for
every UI texture. That is correct for Quiet Rune but must not be assumed
correct for anti-aliased Inter. The approved raster
strategy will test alpha coverage with linear sampling, two-pixel transparent
atlas padding, clamp-to-edge, no mipmaps, and snapped glyph origins/baselines.
Solids and pixel-art item/input icons remain framebuffer-snapped. Filtering is
an atlas property, not a global style guess.

### Audio

`SoundEvent`, `SoundCue`, and SFX gain values exist, but `AudioDevice` exposes
only music start/gain/query/stop/update. There is no bounded UI SFX playback
path. UI audio is therefore deferred. Adding it now would be audio architecture
work, not presentation polish.

## Prompt vocabulary that does and does not match

The prompt names `BitmapFont`, `UiFrame`, `UiDrawCommand`, `TextRenderer`, and
`UiLayoutContext`; all of those exact classes exist.

The proposed generic `UiTheme` only partly exists as game-owned
`GaiaUiTheme`, whose current scope is the Astral/Quiet Membrane HUD. It does
not yet own the product-shell palette, typography roles, general components,
or motion.

Other mismatches or constraints:

- runtime has one font atlas and one font instance, not multi-face/multi-page
  typography;
- `ProductScreenPresenter` hard-codes most menu colors and geometry;
- no general functional icon catalog exists; current icons are item-centric;
- no runtime SVG parser, TTF parser, tween engine, or web UI exists;
- no usable UI SFX playback seam exists despite SFX settings and cue values;
- the Controls screen currently presents only `WASD MOVE`, `MOUSE LOOK`, and
  `ESC BACK`, so the first input-glyph import can remain very small;
- a reduced-motion persisted setting would expand the current settings schema;
  Gate 17.5 should first add a policy seam and defer the user-facing switch.

## Current visual problems

1. **No product-wide hierarchy.** One fixed face, one advance width, and
   nearly one text scale make titles, body copy, metadata, buttons, quantities,
   and diagnostics read as the same layer.
2. **Small-text readability.** Quiet Rune succeeds as a pixel identity accent
   but is too coarse and monospaced for timestamps, world metadata, settings,
   error copy, and dense debug values.
3. **Hard-coded product styling.** `ProductScreenPresenter` owns a second set
   of inline colors and many local spacing numbers, while HUD widgets use a
   partial `GaiaUiTheme`.
4. **Weak state language.** Selected/focused/hovered states are visually close,
   product buttons have no shared component contract, and keyboard focus is
   not a distinct themed state.
5. **Sparse functional iconography.** Product screens rely mostly on words and
   `+`/`-`; the icon atlas cannot express save, load, warning, settings,
   recovery, paging, or input prompts.
6. **Static transitions.** HUD owns a few bounded fades, but menus and modals
   have no consistent response timings. The shell changes state correctly but
   visually feels abrupt.
7. **Font metrics are incomplete.** UV dimensions are treated as glyph ink
   dimensions, so a padded proportional atlas cannot be represented correctly.
   There is no common baseline/line-height contract.
8. **Atlas assumptions are closed.** The loader requires exact 128 by 64
   dimensions and fixed grids, which blocks tightly packed proportional glyphs
   and product icons.
9. **Future-screen risk.** Phase 18/19 would otherwise copy existing magic
   values and create another visual language.

## Design alternatives

### Alternative A — approved: one logical system over measured 1-N physical pages

Build Pixelify display faces and the selected UI family into one logical Gaia
typography system backed by one or more deterministic, tightly packed physical
atlas pages. Add face/metrics/page metadata and semantic roles without adding a
second `TextRenderer` or `UiRenderer`. The real specimen and runtime
measurements decide whether the initial English UI uses one shared page or
separate Pixelify/body pages. Different raster sizes or materially better
nearest-versus-linear sampling are valid reasons to use separate pages.

Advantages:

- preserves one renderer and one font-rendering authority;
- lets the measured result choose the minimum page/bind count that preserves
  Pixelify and body-text clarity;
- smallest GPU/resource-lifecycle change;
- gives precise proportional metrics and hierarchy;
- leaves a tested multi-page seam for later CJK work.

Cost:

- generator, texture identity, and metadata schema must evolve;
- every option must report atlas count, dimensions, RGBA bytes, sampler mode,
  texture-bind impact, and draw-command impact;
- total font atlas memory targets at most 2 MiB, with a hard design-review stop
  before 4 MiB.

### Alternative B — independent atlas page per face

Use separate Pixelify, Inter Regular, Inter Medium, and Inter SemiBold texture
pages from the start.

Advantages: simple per-face generation and flexible future glyph coverage.

Disadvantages: requires more `UiTextureId`/bundle/GPU/batch surface and can add
extra runs when weights alternate. It is not the default, but it remains a
valid measured result if the A/B specimen proves that shared sampling materially
hurts either Pixelify or the body family.

### Alternative C — retain Quiet Rune and only recolor/restyle

This is the lowest infrastructure risk but does not fix dense-text readability,
proportional width, metric correctness, or hierarchy. It is rejected as the
final direction. Quiet Rune may remain a historical/project-owned asset or a
temporary fallback during migration, not a production body face after the
vertical slice is approved.

## Proposed typography stack

### Specimen decision

Compare the following exact content at 100%, 125%, 150%, and Retina-like 200%
framebuffer scales:

```text
GAIA LEGACY
NEW WORLD    LOAD WORLD    SETTINGS
Build a world, preserve its history, and return safely.
MASTER VOLUME                         75%
World Slot: Pale Orbit
Seed: -9223372036854775808
2026-09-01 18:42:07
WARNING — RECOVER BACKUP?
STONE DETAIL  64
PRECISION [3,1,2]  DIRT  VALID
FPS 144 | CHUNKS 81 | MESH 2/0/1
```

Specimen A uses Pixelify Sans display plus Inter UI. Specimen B uses the same
Pixelify display plus IBM Plex Sans UI. Both use identical role sizes, colors,
line lengths, and component bounds.

**Recommendation: Pixelify Sans + Inter.** Inter's screen-oriented tall
x-height, compact familiar shapes, and clear numerals better serve small HUD
values, timestamps, seed extremes, and dense Settings rows. IBM Plex Sans has
more authored technical character and remains a credible challenger, but its
more distinctive forms add width/layout risk without enough benefit for the
functional layer. Pixelify supplies the identity that Inter intentionally does
not. Final human review of the generated specimen remains mandatory before
mass migration.

### Semantic roles

| Role | Face | Nominal logical px | Line height | Intended use |
| --- | --- | ---: | ---: | --- |
| `DISPLAY_TITLE` | Pixelify Sans Bold 700 | 42 | 48 | `GAIA LEGACY`, rare identity title |
| `HEADING_LARGE` | Pixelify Sans SemiBold 600 | 28 | 34 | screen title |
| `HEADING` | Inter SemiBold 600 | 20 | 26 | section/modal title |
| `BODY` | Inter Regular 400 | 16 | 22 | help and explanatory copy |
| `BUTTON_LABEL` | Inter SemiBold 600 | 16 | 20 | interactive labels |
| `HUD_LABEL` | Inter Medium 500 | 14 | 18 | compact gameplay labels |
| `HUD_VALUE` | Inter SemiBold 600 | 15 | 18 | counts, percentages, selected values |
| `SMALL_CAPTION` | Inter Regular 400 | 12 | 16 | timestamps and secondary metadata |
| `DEBUG` | Inter Medium 500 | 12 | 15 | compact debug metrics |

The generated Latin glyph set is the union of production strings plus
printable ASCII, infinity, U+FFFD, and any explicitly tested punctuation. It
does not silently include large Unicode ranges. CJK packaging is deferred.

Game-owned `GaiaTypographyRole` resolves to immutable engine text-style data.
Engine code owns generic face/page/metrics values but knows nothing about Gaia
semantic role names. Presenters request roles rather than direct face files or
weights.

### Font data contract

The evolved font metadata must contain:

- face ID and atlas page ID;
- source em/pixel size and scale policy;
- ascent, descent, baseline, and line height;
- per-glyph code point, ink rectangle, padded atlas rectangle, advance,
  X/Y bearings, and fallback identity;
- deterministic page dimensions, padding, pixel format, and filtering;
- source SHA-256 and generator schema/version.

`TextRenderer.measure` and `append` must use the same advances and metrics.
Every glyph origin and baseline snaps through `UiLayoutContext`; the glyph
quad then uses its real ink bounds. Missing glyph diagnostics remain bounded
to once per code point.

## Component language

The implementation should add game-owned, pure draw-command component
presentation helpers. They do not become another renderer or input system.
Existing screen presenters continue to own immutable layout and hit regions.

Required component contracts:

- primary, secondary, destructive, and icon button;
- text/seed input;
- slider;
- toggle;
- stepper (`-`, value, `+`);
- selectable world-slot/card with health/recovery state;
- inventory/body slot preserving Shared Core and detached Creative truth;
- HUD chip and DETAIL state chip;
- tooltip/help row;
- input prompt;
- progress/loading/saving indicator;
- modal and error/acknowledgement panel;
- explicit keyboard focus ring.

Every interactive component resolves `normal`, `hover`, `keyboardFocus`,
`pressed`, `selected` where applicable, `disabled`, and
`destructive/error` states from the same theme. Hover and keyboard focus are
separate inputs. Components emit only immutable commands and never receive
World, Save, Inventory, WorldItem, Chunk, or DETAIL mutation capabilities.

## Functional and identity icon plan

Use one extended Gaia UI icon atlas and one `UiIconId` presentation catalog.
Canonical gameplay item icons remain keyed by canonical `ResourceLocation`;
functional icon IDs are a separate presentation namespace inside the same
asset owner, not an item registry or renderer.

Lucide is limited to the exact generic functions in the whitelist. The source
manifest maps every Gaia semantic ID to one exact upstream SVG filename, pinned
tag/commit, source-byte SHA-256, and generated atlas entry. In particular,
`SAVE_RECOVERY` maps to the actual Lucide 1.27.0
`icons/archive-restore.svg` candidate rather than a nonexistent `recover`
filename; the specimen must still confirm that its semantics fit. Build-time
conversion normalizes each to a common 24-unit optical box, two-unit-equivalent
stroke, consistent padding, white straight-alpha pixels, and deterministic
16/20/24-pixel derivatives as measurements require. The runtime never opens
SVG files.

Gaia-specific marks and tool/detail states are created as project-owned source
geometry in the existing deterministic Java generator (or reviewed small
source rasters), recorded as project-owned in provenance. They do not derive
gameplay capability from their pixels.

## Motion foundation

### Tokens

| Token | Duration | Easing | Visual range |
| --- | ---: | --- | --- |
| hover/focus | 120 ms | ease-out cubic | alpha/border emphasis |
| press | 80 ms | ease-out cubic | alpha plus <=2 logical px down offset |
| selected/tab/chip | 160 ms | ease-in-out cubic | fill/border emphasis |
| tooltip enter/exit | 160/200 ms | ease-out/ease-in cubic | opacity plus <=4 px |
| modal enter/exit | 200/220 ms | ease-out/ease-in cubic | opacity plus <=8 px |
| toast enter/exit | 180/240 ms | ease-out/ease-in cubic | opacity plus <=8 px |
| screen enter/exit | 240/240 ms | ease-out/ease-in cubic | opacity plus <=12 px |
| existing inventory selection | 150 ms | existing bounded interpolation | border/emphasis only |

One presentation clock in the existing owner-thread `ProductLoop` supplies
monotonic frame delta. It does not change gameplay fixed-step timing and does
not create another loop. One bounded `ProductUiMotionState` (final name to be
audited in the implementation plan) tracks only current screen/component
transitions by stable control ID and produces an immutable motion snapshot for
the presenter.

Rules:

- endpoint-clamped normalized progress; no queued callbacks;
- a frame gap above 250 ms snaps non-essential transitions to their current
  target, preventing Alt+Tab catch-up motion;
- hover reversal reuses the current normalized progress;
- closing a screen discards its bounded state immediately;
- animations change only paint transform/opacity, never `UiHitRegion`;
- loading/saving may remain the only bounded continuous consumer;
- reduced-motion policy sets non-essential translation/scale to zero and
  shortens duration to at most 40 ms while preserving visible state changes.

Gate 17.5 introduces the reduced-motion policy seam but does not add a saved
Settings field unless a later implementation audit proves the schema change is
narrow and separately approved.

## DPI and raster strategy

1. Generate each face at a reviewed canonical raster size with real metrics,
   anti-aliased alpha, two transparent padding pixels, and stable row/skyline
   packing.
2. Commit generated RGBA8 PNG and strict metadata. Runtime loads no TTF/OTF.
3. Use linear filtering for anti-aliased proportional font alpha if the Gate
   17.5B specimen proves it crisper at 100/125/150/200%; keep nearest for
   pixel-art item/input icons. This may require per-texture sampler metadata,
   not a global filter switch.
4. Snap baseline and glyph origins in framebuffer space. Do not independently
   round the measured pen advance in a way that diverges from rendering.
5. Test atlas padding/bleed, baseline stability, clipping, truncation, and
   asymmetric X/Y content scale.
6. Ship one logical Latin typography catalog initially. It may use one or more
   measured physical pages. Metadata carries explicit page IDs, sampler modes,
   and a fallback chain so a later CJK page can be added without changing
   semantic roles. Adding CJK still requires its own memory/license approval.

## Deterministic build and packaging

The existing `tools` pipeline remains the only asset generator. Gate 17.5B
should extend `UiAssetGenerator` rather than add a second build tool.

Conceptual deterministic flow:

```text
reviewed vendored TTF/SVG/PNG sources + license receipts
    -> checked generator version and explicit glyph/icon manifest
    -> deterministic raster/packing
    -> generated font/icon PNG + strict JSON metadata
    -> byte comparison in :tools:verifyGeneratedUiAssets
    -> JAR/installDist packaged-resource checks
```

The provenance document records official URL, release/tag/commit, original
filename, downloaded SHA-256, license and bundled notice, local source path,
generated derivative path/hash, conversion command, selected glyph/icon list,
and any recolor/rasterization. No OS fonts, CDN, per-frame decode, or absolute
filesystem path may participate.

## Expected implementation surface after approval

- add generic face/page/style identities or equivalent immutable records;
- extend `TextRenderer` measure/append APIs while preserving a compatibility
  path during migration;
- extend `UiAssetBundle` metadata and texture sampling configuration;
- only add multiple font texture pages if the one-page measured target fails;
- preserve `UiRenderer`, `UiBatchPlanner`, shader, and main-thread ownership.

Likely game changes:

- evolve `GaiaUiAssetLoader`, `GaiaUiAssets`, and icon metadata;
- evolve `GaiaUiTheme` into immutable product/HUD token records;
- add `GaiaTypographyRole` and pure style/component presentation helpers;
- migrate `ProductScreenPresenter`, then HUD widgets, without changing input,
  layout truth, shell state, or gameplay state;
- add bounded product presentation motion owned by the current product loop.

Likely tools/resources/docs changes:

- evolve `UiAssetGenerator` and font/icon generators;
- add exact selected source files and licenses only after approval;
- update `ui-assets.json`, generated atlas/metadata, resource index, package
  verification, `THIRD_PARTY_NOTICES.md`, and `docs/ui-asset-provenance.md`;
- add `docs/architecture/ui-visual-system.md` and Gate implementation notes;
- preserve prior historical architecture documents.

No runtime dependency is proposed.

## Gate sequence after human approval

### Gate 17.5B — typography, icon, and asset pipeline

1. Create exact Inter/Plex/Pixelify source receipts and render an A/B specimen.
2. Human confirms Inter or Plex and Pixelify display sizing.
3. TDD generic font metrics, semantic roles, deterministic atlas, filtering,
   measure/render agreement, missing glyphs, and provenance.

5. Run product/HUD focused tests, resource checks, and real-game typography
   inspection across Main Menu, New World, World Slots, Settings, HUD, DETAIL,

### Gate 17.5B.5 — world-first main-menu visual direction

Before broad runtime migration, compare three deterministic 1280x720 title
concepts with identical functional content and the approved Pixelify/Inter
typography:

- **Gaia Panorama:** the project-owned Gaia landscape remains prominent beneath
  a directional gradient, minimal navigation, and restrained contour traces;
- **Orbital Legacy:** the same Gaia world receives a cooler treatment and sparse
  broken-ring/orbital motifs;
- **Dark Signal:** a deliberately dark atmospheric treatment tests a larger
  emblem, topographic traces, and signal ticks while retaining real terrain.

All concepts use a project-owned provisional emblem composed from a broken
planetary ring, terrain horizon, and subtle quarter-grid cells. It is a direction
study, not the final game logo. The intended production path is project-owned
vector source, deterministic build-time rasterization, then the existing Gaia UI
asset system. No runtime SVG renderer is proposed.

The preferred Phase 17.5 runtime background architecture is a deterministic set
of three or four project-owned Gaia captures with a very slow pan/crossfade. The
existing `UiRenderer` remains the sole renderer. A narrow hero texture-page
binding may allow the current and next RGBA8 images to coexist during a
crossfade; it must not introduce a second World, renderer, simulation, save
lifecycle, shader, or GPU authority.

Stop after the three review concepts. Gate 17.5C begins only after a human
selects or combines a direction.

### Gate 17.5D — migrate all existing surfaces

### Gate 17.5E — packaging and acceptance

The detailed executable implementation plan is deliberately not written until

## Validation strategy

Prefer deterministic structural tests over cross-GPU framebuffer hashes:

- semantic role and token resolution;
- font source/provenance manifests and generated byte hashes;
- actual metrics, baseline, line height, measure/render agreement, missing
  glyph, clipping, truncation, and DPI matrices;
- icon IDs, normalized bounds, deterministic conversion, and packaging;
- component normal/hover/focus/pressed/selected/disabled/destructive command
  snapshots;
- motion t=0/mid/end, clamp, interruption, reversal, screen destruction,
  focus loss, reduced motion, and unchanged hit regions;
- screen/HUD command and layout snapshots;
- human visual review for aesthetics on bright/dark world scenes.

Performance reporting must include draw commands, glyph/icon quads, texture
binds, atlas dimensions/bytes, active motion-state count, and observable
allocations for Main Menu, World Slots, Settings, HUD, and DETAIL tooling.

## Explicit non-goals

- no second renderer, HUD, navigation system, font renderer, icon renderer,
  animation loop, or gameplay authority;
- no runtime TTF/SVG/network/browser/UI framework;
- no new dependency without a stop and separate approval;
- no UI SFX until the existing audio authority exposes a bounded seam;
- no CJK package without shipping strings, memory measurements, and complete
  license inventory;
- no blur, bloom, full-screen UI post-process, real-time cinematic showcase
  world, or shader rewrite; deterministic project-owned Gaia hero captures are
  allowed;
- no gameplay, save, inventory, world, DETAIL, Phase 18, or Phase 19 changes;
- no broad responsive-web layout rewrite;
- no copied Minecraft assets or visual identity;
- no entire upstream font/icon/UI package imports.

Typography, palette, asset scope, motion, and deferred work are approved. The
remaining decision is the Gate 17.5B.5 title-screen direction: select Concept A,
Concept B, Concept C, or an explicit combination before Gate 17.5C runtime
migration.
